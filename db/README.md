# 회원 및 지갑 인증 스키마

`migrations/001_create_identity_and_sessions.sql`은 PostgreSQL 16 기준 초기 스키마다.
SQL 파일 생성과 실제 DB 적용은 별개다. 기존 테이블이 있으면 실패하며, 파일 전체를 한 트랜잭션으로 적용한다.
이 파일은 로그인 API나 자동 갱신 작업을 실행하지 않는다.

## 테이블 관계

- `users`: 로그인 수단과 무관한 서비스 회원. 기여 및 그리기 제한은 이 회원 ID를 기준으로 한다.
- `user_wallets`: 회원당 여러 지갑을 허용한다. `(chain_namespace, address_key)`는 전체 회원에서 유일하다.
- `auth_challenges`: 회원가입 전에도 발급하는 일회용 로그인 요청. 회원 FK는 없다.
- `auth_sessions`: 회원당 여러 기기의 로그인을 허용하는 서버 세션.

지갑 앱 이름은 식별 기준이 아니다. 같은 Solana 주소는 Phantom 또는 다른 앱으로 접속해도 같은 회원이다.
현재 지원할 검증 방식은 `solana_siws`뿐이다. DB의 문자열 확장 가능성이 다른 체인 지원을 의미하지는 않는다.
Solana devnet/mainnet은 로그인 요청과 온체인 작업에서 구분하며, 회원의 지갑 식별자를 나누지 않는다.
다른 체인, 특히 네트워크별 스마트 계정을 도입할 때는 주소 정규화와 식별 범위를 다시 설계해야 한다.

새 지갑을 기존 회원에게 연결하는 API는 후속 범위다. 로그인 세션과 새 지갑 서명을 모두 확인해야 하며,
연결 요청은 발급한 회원/세션 및 목적에 묶어야 한다. 이미 다른 회원에게 연결된 지갑을 자동 병합하지 않는다.

## 인증 및 갱신 정책

초기 정책은 challenge 5분, 세션 활동 만료 7일, 최초 로그인으로부터 절대 만료 30일이다.
DDL의 기본값은 초기 발급 편의용이다. 애플리케이션이 시각을 직접 지정할 경우 모든 값을 같은 기준 시각으로 계산한다.

1. 서버가 암호학적 난수 nonce와 브라우저 바인딩용 임시 쿠키를 발급한다.
2. 서버가 발급한 SIWS 입력을 저장한다. JSON과 컬럼의 nonce/만료 시각을 일치시킨다.
3. 서명, 공개키/주소 일치, 도메인, URI, 체인, nonce, 유효기간, 브라우저 바인딩을 검증한다.
4. DB 트랜잭션에서 `consumed_at IS NULL AND expires_at > 현재시각`인 challenge만 조건부 UPDATE한다.
   반환 행이 없으면 실패한다. challenge 소비, 회원/지갑 생성 또는 조회, 세션 생성을 함께 커밋한다.
5. 같은 지갑의 동시 가입은 UNIQUE 제약으로 방어한다. 충돌한 생성 작업은 롤백한 뒤 기존 회원 조회로 재시도한다.
6. 활성 회원이고, 폐기되지 않았으며, 두 만료 시각 전인 세션만 인증 및 갱신한다.
7. 갱신 시 `expires_at = LEAST(현재시각 + interval '7 days', absolute_expires_at)`로 설정한다.
   `last_seen_at`도 갱신하고 쿠키의 만료 시각을 DB와 맞춘다. 예를 들어 1시간 단위로 쓰기를 제한할 수 있다.
   이 경우 마지막 활동 시각은 정확한 접속 감사 기록이 아니라 갱신 시점의 근사치다.
8. `absolute_expires_at`은 갱신하지 않는다. 만료 또는 폐기된 세션은 되살리지 않고 재인증한다.

세션 토큰은 최소 256비트의 암호학적 난수로 생성하고 DB에는 SHA-256 소문자 16진수 해시만 저장한다.
운영 쿠키에는 `HttpOnly`, `Secure` 및 배포 토폴로지에 맞는 `SameSite`를 적용한다.
상태 변경 API에는 Origin 검증 등 CSRF 방어를 적용한다. 지갑 연결 해제만으로 서버 세션이 폐기되지는 않는다.
로그아웃 API는 세션을 폐기하고 쿠키를 삭제한다. 회원 정지/탈퇴 시 기존 세션도 사용하지 못하게 한다.

`users.updated_at`은 애플리케이션이 변경 시 갱신한다. DB 트리거는 없다.
회원 삭제의 연쇄 삭제는 사용하지 않는다. 탈퇴 및 주소 재사용 정책이 정해지기 전에는 회원/지갑 기록을 물리 삭제하지 않는다.
지갑만으로는 한 사람이 여러 지갑을 만들어 새 회원으로 가입하는 것을 막을 수 없다.

## 접근과 적용

Supabase의 공개 Data API를 통해 인증 테이블이 노출되지 않도록 네 테이블 모두 RLS를 활성화하고,
브라우저 접근 정책은 만들지 않는다. NestJS는 서버에만 보관한 DB 자격 증명으로 접근한다.
테이블 소유자 또는 적절한 BYPASSRLS 및 테이블 권한을 가진 서버 역할이 필요하다.
일반 제한 역할을 사용할 경우 서버 전용 RLS 정책과 GRANT를 별도 구성해야 한다.
브라우저에 DB 비밀번호, 관리자 키 또는 세션 토큰 해시를 전달하지 않는다.

DB 접속 환경변수를 설정한 뒤 대상 DB를 확인하고 한 번 적용한다.

```bash
psql -v ON_ERROR_STOP=1 -f db/migrations/001_create_identity_and_sessions.sql
```

이미 적용한 초기 파일을 수정해 재실행하지 않는다. 후속 변경은 새 번호의 마이그레이션으로 남긴다.
만료된 challenge 및 세션 정리는 별도 작업으로 구현한다.

## 스키마 검증

초기 마이그레이션을 적용한 전용 테스트 DB에서 다음을 실행한다. 테스트 역할 생성 권한이 필요하다.

```bash
psql -v ON_ERROR_STOP=1 -f db/tests/identity_constraints.sql
```

여러 지갑 연결, 주소 중복, Solana 대소문자 보존, 탈퇴 상태, 세션 만료 및 갱신 조건,
challenge 재사용 방지 쿼리, FK 삭제 제한, RLS 조회 차단을 검사하고 데이터를 롤백한다.
서명 검증, 실제 쿠키 갱신, 동시 요청 및 인증 API 검증은 API 구현 시 별도로 수행한다.
