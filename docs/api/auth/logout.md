# POST /api/auth/logout — 현재 세션 로그아웃

- 상태: 설계 확정, 구현 예정. 현재 제공 중인 API가 아니다.
- 설계 기준일: 2026-10-01
- 경로는 `API_PREFIX=api` 기준이며 경로 접두사를 비우면 `/auth/logout`이다.

## 목적과 인증

요청에 제출된 세션 토큰 하나가 가리키는 행을 폐기하고 해당 브라우저의 인증 쿠키를 삭제한다. 같은 사용자의 다른 세션은 다른 브라우저의 세션을 포함해 유지한다. 사용자 계정과 연결된 지갑은 삭제하지 않는다. 같은 브라우저에서 동시에 생성되는 다른 세션까지 찾아 폐기하는 계약은 아니다.

유효한 로그인 세션을 요구하지 않는다. 세션이 없거나 이미 만료·폐기되었어도 반복 로그아웃은 성공한다. 허용된 요청 출처 검증은 항상 적용한다.

## 요청

| 항목 | 계약 |
| --- | --- |
| 경로 매개변수 | 없음. |
| 쿼리 | 사용하지 않음. 전달되어도 무시. |
| `Origin` | 필수. 허용된 프론트 요청 출처와 정확히 일치. |
| `Content-Type` | 필수 아님. JSON을 보낼 때는 `application/json` 또는 `application/json; charset=utf-8` 사용. |
| 본문 | 허용 필드 없음. 생략·전달 모두 가능하며 업무 입력으로 사용하지 않음. |
| 쿠키 | 현재 세션 쿠키 선택. 성공 시 세션·브라우저 연결 쿠키 삭제 헤더를 모두 발급. |

```http
POST /api/auth/logout
Origin: https://app.example.com
Content-Type: application/json
Cookie: __Host-cameo_session=<opaque-session-token>

{}
```

프론트는 `credentials: 'include'`를 사용한다. userId, 지갑 주소, 세션 ID를 본문으로 받아 폐기 대상을 선택하지 않는다.

정의되지 않은 쿼리는 모두 무시한다. 본문에 허용 필드가 없으므로 추가 필드와 값도 모두 무시하며 DTO로 로그인 입력 검증을 수행하지 않는다. 본문·`Content-Type` 누락 또는 사용하지 않는 매체 타입 자체를 이유로 400을 반환하지 않는다. 전역 HTTP 파서가 선택한 JSON·폼 본문은 파싱·크기 제한을 따르고, 파싱하지 않는 본문은 업무 입력으로 사용하지 않는다. 문법·디코딩 오류는 400, 파서의 크기 제한 초과는 413, 지원하지 않는 charset·Content-Encoding은 415다. 로그인 전용 `Content-Type` 필수 검사를 이 API에 적용하지 않는다.

## 요청 쿠키 처리

선택 세션 토큰은 난수 32바이트를 표현한 패딩 없는 Base64url 43자다. 길이·문자 집합·디코딩 결과 32바이트·재인코딩 일치를 확인하며 값을 URL 디코딩하거나 형식을 보정하지 않는다. 같은 이름의 쿠키가 두 개 이상이면 값이 같아도 미제출로 취급하며 첫 값·마지막 값을 임의로 선택하지 않는다.

정규 토큰만 SHA-256 소문자 16진수 64자 해시로 조회한다. 누락·빈 값·형식 오류·동일 이름 중복은 DB 작업 없이 200이며 두 쿠키 삭제 헤더를 발급한다. 연결 쿠키의 값·형식·중복 여부는 폐기 대상을 정하거나 성공을 막는 데 사용하지 않는다. 허용된 요청 출처 검증은 세션 쿠키 유무와 관계없이 먼저 적용한다.

## 처리와 성공 응답

형식이 맞는 토큰은 같은 트랜잭션에서 `token_hash`가 일치하고 `revoked_at IS NULL`인 행만 조건부 갱신한다. 기존 `session/`의 제출 세션 폐기 정책을 사용해 `revoked_at=GREATEST(clock_timestamp(), created_at)`으로 저장한다. 만료된 미폐기 행도 폐기하며 이미 폐기된 행의 최초 `revoked_at`은 유지한다. 일치 행이 없어도 200이다. 만료·사용자 활성 상태를 성공 조건으로 요구하지 않는다.

세션 행의 조건부 갱신은 `/me`의 연장과 같은 행 잠금에 참여한다. 로그아웃은 세션 행만 갱신하고 그 뒤 사용자 행을 잠그지 않아 로그인·`/me`의 사용자 후 세션 잠금 순서와 충돌하지 않게 한다. `expires_at`, `absolute_expires_at`, `last_seen_at`을 갱신하거나 `revoked_at`을 null로 되돌리지 않는다.

HTTP 200, `Cache-Control: no-store`.

```json
{
  "statusCode": 200,
  "success": true,
  "data": {
    "loggedOut": true
  }
}
```

성공 응답의 `loggedOut`은 항상 참(true)인 불리언 값이며 제출된 토큰에 대한 처리가 끝났다는 의미다. 로그아웃은 세션을 연장하거나 새 세션을 만들지 않는다. 유효한 형식의 토큰으로 DB 작업이 필요하면 커밋 성공을 확인한 뒤 쿠키를 삭제한다. 다른 진행 중 로그인이나 탭에서 생성하는 세션까지 폐기됐다는 의미는 아니다.

## 쿠키

운영 응답은 두 쿠키를 모두 삭제한다.

```http
Set-Cookie: __Host-cameo_session=; Max-Age=0; Path=/; HttpOnly; Secure; SameSite=Lax
Set-Cookie: __Host-cameo_auth_binding=; Max-Age=0; Path=/; HttpOnly; Secure; SameSite=Lax
```

로컬 HTTP는 `cameo_session`과 `cameo_auth_binding` 이름을 사용하고 Secure를 생략한다. Domain은 환경에 관계없이 생략한다. 요청에 두 쿠키가 없어도 삭제 헤더를 모두 발급하며 두 `Set-Cookie` 헤더 중 하나를 덮어쓰지 않는다.

연결 쿠키 삭제는 DB의 미사용 챌린지를 소비·삭제하거나 이미 전송된 요청을 취소하지 않는다. 삭제된 쿠키 상태로 보내는 후속 로그인은 기존 연결값을 제출할 수 없으므로 새 챌린지부터 시작한다. 이미 기존 연결값을 실어 보낸 로그인은 쿠키 삭제 후에도 서버에서 완료될 수 있다.

이 API는 서비스 세션을 폐기한다. 프론트의 지갑 연결 해제는 별도로 수행할 수 있으며, 지갑 연결 해제만으로 서버 세션이 폐기됐다고 표시하지 않는다.

## 구현 책임과 HTTP 경계

`logout/`에 컨트롤러와 유스케이스를 두고 출처는 기존 `auth-origin`, 토큰 검증·해시는 `auth-secret`, 쿠키 읽기·이름·속성은 `auth-http`를 사용한다. 유스케이스가 출처 확인과 제출 세션 폐기를 조정하고 기존 `SessionRepository`를 같은 불투명 `TransactionContext`로 호출한다. DB 작업이 없는 입력은 트랜잭션을 열 필요가 없다.

이 API에는 유효한 세션·활성 사용자를 요구하는 인증 가드를 적용하지 않는다. 컨트롤러는 확정된 유스케이스 결과를 받은 뒤 두 쿠키를 삭제하고 공개 성공 응답을 반환한다. DB 오류를 잡아 성공 결과로 바꾸지 않으며 공통 오류 필터에 인증 쿠키 정책을 넣지 않는다. 성공·실패 모두 `Cache-Control: no-store`이고 토큰 원문·해시·연결값을 JSON과 로그에 포함하지 않는다.

본문 파서가 발생시킨 입력 오류는 HTTP 계층에서 아래 400·413·415 공개 예외로 변환한다. 현재 공통 필터는 HTTP 예외로 변환되지 않은 일반 오류를 500으로 처리하므로, 구현 시 프레임워크의 기본 변환만으로 이 계약을 충족한다고 가정하지 않는다. 이 변환에는 DB 접근이나 인증 쿠키 변경을 포함하지 않는다.

## 오류 응답과 재시도

| 상태 / 코드 | 조건 | 공개 메시지 | 쿠키 |
| --- | --- | --- | --- |
| 400 `BadRequestException` | HTTP 요청 파싱 실패(잘못된 JSON 문법 등) | 요청 파싱 오류 메시지 | 변경하지 않음 |
| 413 `PayloadTooLargeException` | HTTP 파서의 본문 크기 제한 초과 | `요청 본문이 너무 큽니다.` | 변경하지 않음 |
| 415 `UnsupportedMediaTypeException` | 파서가 선택한 본문의 지원하지 않는 charset·Content-Encoding | `지원하지 않는 본문 인코딩입니다.` | 변경하지 않음 |
| 403 `AUTH_ORIGIN_NOT_ALLOWED` | 요청 출처 누락·null·비허용 값 | `허용되지 않은 요청 출처입니다.` | 변경하지 않음 |
| 429 `ThrottlerException` | IP 한도 초과 | `ThrottlerException: Too Many Requests` | 변경하지 않음 |
| 500 `INTERNAL_SERVER_ERROR` | DB·커밋 확인·응답 처리 등 내부 실패 | `Internal server error` | 아래 실패 단계에 따름 |

```json
{
  "statusCode": 500,
  "success": false,
  "code": "INTERNAL_SERVER_ERROR",
  "message": "Internal server error",
  "error": "Internal Server Error",
  "traceId": "c9f2ea59-4f07-4b6d-a1b0-eb546ee18265"
}
```

세션 없음·잘못된 쿠키·만료·이미 폐기는 401이 아닌 200이다. 본문·쿼리는 폐기 대상이나 성공 여부에 영향을 주지 않는다. 요청 출처 검증이나 요청 파싱 실패를 멱등 성공으로 바꾸지 않는다. DB 실패를 성공으로 표시하지 않는다.

### 실패 단계와 재시도

다음 표는 이번 요청이 일으키는 변경만 설명한다. 다른 동시 요청의 변경을 되돌리지 않는다. 쿠키 변경은 서버의 삭제 헤더 발급이며 브라우저 수신까지 보장하지 않는다.

| 결과 | 제출된 세션 DB 상태 | 세션·연결 쿠키 |
| --- | --- | --- |
| 200, 존재하는 미폐기 행 | 폐기 커밋 | 모두 삭제 |
| 200, 미제출·잘못된 형식·중복·미존재·이미 폐기 | 변경 없음 | 모두 삭제 |
| 400·413·415 파싱 오류 / 403 출처 오류 / 429 요청 제한 | 변경 없음 | 변경 헤더 발급 안 함 |
| 500 내부·DB 오류, 롤백 확인 | 이번 요청의 폐기 롤백 | 변경 헤더 발급 안 함 |
| 500 COMMIT 결과 확인 실패 | 폐기 커밋 여부 불명 | 변경 헤더 발급 안 함 |
| 500 업무 결과 확정 후 응답 처리 오류 | 확정된 폐기 또는 미변경 결과 유지 | 전달 여부 불명 |

확인된 커밋은 쿠키 구성·응답 직렬화·전송 실패로 되돌리지 않는다. DB 작업 없는 성공도 쿠키 처리 중 실패하면 공개 500이 될 수 있으며 DB는 변경하지 않는다. 응답 전송 전 오류는 공개 500으로 처리하고 이미 전송을 시작했다면 연결이 종료될 수 있다. 쿠키는 미전달·일부 전달·전달 여부 불명일 수 있다. 실패 단계나 DB 내부 상태를 JSON에 노출하지 않는다.

동일 토큰을 반복 제출하면 같은 최종 폐기 상태를 유지한다. 응답 유실이나 500 후에는 새 로그인을 시작하지 않은 상태에서 로그아웃을 재시도할 수 있다. 쿠키가 이미 삭제됐다면 토큰 없는 200으로 마무리된다. 브라우저는 재시도 시점의 쿠키를 보내므로 그 사이 새 로그인했다면 재시도는 새 세션을 폐기할 수 있다. 자동 재시도를 새 로그인 흐름과 겹치게 실행하지 않는다. 429는 `Retry-After` 이후 재시도한다.

### 인증 요청 경합과 프론트 처리

폐기된 DB 행은 `/me` 연장으로 되살리지 않는다. 늦은 `/me` 응답이 같은 폐기 토큰을 브라우저에 재설정해도 해당 토큰은 인증되지 않는다. 이 보장은 새로 생성된 다른 세션에는 적용되지 않는다.

S0을 제출한 로그인과 로그아웃이 겹치면 로그아웃은 S0만 폐기하고 로그인은 S1을 만들 수 있다. 늦은 로그인 응답이 S1을 설정하면 다시 로그인한 상태가 될 수 있고, 늦은 로그아웃 응답이 쿠키를 삭제하면 S1은 DB에서 활성 상태지만 브라우저는 토큰을 잃을 수 있다. 연결 쿠키 삭제도 이미 전송된 로그인을 취소하지 않는다. 서버는 브라우저 전체의 로그아웃 우선 처리나 진행 중 새 세션의 일괄 폐기를 보장하지 않는다.

프론트는 로그아웃 흐름이 시작되면 새 챌린지·로그인과 자동 `/me` 조회를 막고 이미 보낸 인증 요청의 응답 처리를 마친 뒤 로그아웃을 보낸다. 로그아웃 응답·재시도 처리가 끝나기 전 새 로그인 흐름을 시작하지 않는다. 오래된 응답 JSON을 무시하는 것만으로는 `Set-Cookie`를 막지 못하며 요청 취소·네트워크 오류도 서버 트랜잭션 취소를 보장하지 않는다.

여러 탭은 쿠키를 공유하며 같은 탭의 직렬화만으로 탭 사이 경합을 제거하지 못한다. 다중 탭의 단일 활성 세션은 보장하지 않는다. 경합 후에는 진행 중 요청이 끝난 뒤 [현재 사용자 API](me.md)로 현재 상태를 확인한다. 로그아웃 의도가 유지된다면 다른 로그인과 겹치지 않게 현재 쿠키로 로그아웃을 다시 수행한다.

## 완료 검증

아래 항목은 구현 시 확인할 기준이며 현재 API를 실행해 확인한 결과가 아니다.

- 현재 세션이 폐기되고 두 쿠키가 동일 적용 범위로 삭제되는지 확인한다.
- 다른 브라우저 세션과 사용자·지갑 행을 유지하는지 확인한다.
- 세션 없음·잘못된 쿠키·만료·이미 폐기된 경우 200인지 확인한다.
- 본문·쿼리를 생략하거나 추가로 전달해도 현재 쿠키가 가리키는 세션만 폐기하는지 확인한다.
- 본문 파서의 문법·디코딩 오류 400, 크기 제한 초과 413, 지원하지 않는 인코딩 415에서 DB·쿠키를 변경하지 않는지 확인한다.
- 반복 로그아웃이 최초 폐기 시각을 바꾸지 않는지 확인한다.
- 비허용 요청 출처에서는 폐기·쿠키 삭제가 발생하지 않고 DB 실패는 성공으로 표시되지 않는지 확인한다.
- 세션 연장과 경합하더라도 로그아웃된 토큰이 다시 인증되지 않는지 확인한다.
- 동일 값 중복 쿠키·비정규 Base64url은 DB 작업 없이 200이며 두 삭제 헤더를 발급하는지 확인한다.
- 활성 세션 여부·사용자 정지·탈퇴와 무관하게 제출된 토큰 하나만 폐기하는지 확인한다.
- `/me`와 경합하는 조건부 폐기가 최초 폐기 시각을 유지하고 사용자 행을 추가로 잠그지 않는지 확인한다.
- 롤백 확인·COMMIT 결과 불명·커밋 후 쿠키 처리 실패에서 DB와 쿠키 결과를 구분하는지 확인한다.
- 연결 쿠키 삭제가 이미 전송된 로그인이나 DB 챌린지 소비를 취소한 것으로 취급되지 않는지 확인한다.
- 늦은 로그인·로그아웃 응답의 쿠키 경합과 새 로그인 뒤의 재시도 영향을 프론트가 처리하는지 확인한다.
