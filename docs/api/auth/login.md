# POST /api/auth/login — 지갑 로그인

- 상태: 구현 완료. 구현 당시 HTTP·PostgreSQL 통합 검증을 마쳤으며, 검증용 테스트 코드는 저장소에서 제거했다.
- 설계 기준일: 2026-10-01
- 경로는 `API_PREFIX=api` 기준이며 경로 접두사를 비우면 `/auth/login`이다.

## 목적과 인증

[챌린지 발급](challenges.md)에서 받은 입력에 대한 Solana SIWS 서명을 검증한다. 로그인 세션 없이 호출할 수 있으나 챌린지를 발급받은 브라우저의 연결 쿠키가 필요하다. 기존 로그인 쿠키가 있어도 새 지갑 증명을 검증하며, 성공할 때 요청에 제출된 기존 세션을 폐기하고 새 세션 쿠키를 발급한다. 브라우저별로 활성 세션 하나만 존재하도록 보장하는 계약은 아니다.

Phantom은 첫 프론트 연결·검증 대상이다. 서버의 지원 기준은 지갑 브랜드가 아니라 Solana SIWS 메시지와 Ed25519 서명이다. 현재 계약에 맞는 증명을 반환하는 다른 Solana 지갑도 같은 API를 사용한다. 같은 Solana 주소로 다른 지갑 앱에서 로그인해도 기존 계정을 사용한다.

서버는 지갑 앱 이름이나 `isPhantom` 주장으로 신원을 판단하지 않는다. 프론트는 선택한 지갑의 `solana:signIn` 등 SIWS 기능 지원 여부를 확인하고, 지갑별 연결·서명 호출을 담당한다. HTTP API 이름은 `login`이며 Wallet Standard의 `signIn`과 챌린지 응답의 `signInInput`은 표준 연동에 사용하는 이름으로 유지한다.

## 지갑 확장과 구현 경계

- `login/`은 챌린지 확인·소비, 계정 확인·생성, 세션 발급과 트랜잭션을 조정한다. Phantom SDK나 지갑 브랜드 분기를 넣지 않는다.
- `siws/`는 Solana SIWS 입력 생성·메시지·주소·서명 검증을 담당한다. 검증에 성공하면 `chainNamespace`, `address`, `addressKey`로 구성된 검증된 지갑 정보를 로그인 흐름에 전달한다. 현재 값은 `solana`, 검증한 주소, 같은 주소다.
- `wallet-account/`는 검증된 `(chainNamespace, addressKey)`로 계정을 찾고, `session/`은 서비스 세션을 처리한다. 지갑 앱 이름은 계정 식별자에 포함하지 않는다.
- 검증 방식은 DB에 저장된 챌린지의 `auth_method`로 결정한다. 현재는 `siws`만 지원하며, 클라이언트가 보낸 `wallet`, `provider`, `authMethod`, `chainNamespace` 등 추가 필드는 제거하고 검증 방식이나 체인을 바꾸는 데 사용하지 않는다.
- 같은 SIWS 계약을 지원하는 지갑 추가는 프론트 연결 구현과 호환성 검증으로 진행한다. 다른 체인이나 인증 방식은 해당 방식의 발급·검증 구현과 공개 API 계약을 별도로 확장해야 한다. 현재 Base58 주소·Ed25519·SIWS 입력 계약이 모든 체인을 지원한다는 의미는 아니다.

위 경계에 따라 로그인 구현을 분리했다. `siws/`는 입력 생성과 Wallet Standard 표준 증명 검증을 담당하고, `wallet-account/`와 `session/`은 지갑 브랜드와 독립적으로 계정·세션을 처리한다. 발급과 검증 대상은 현재 Solana SIWS다.

이번 로그인 구현의 범위는 이 API, SIWS 증명 검증, 계정·지갑 조회 및 생성, 세션 발급·기존 세션 폐기, 401 업무 오류 매핑과 필요한 DB 기준 SQL이다. [현재 사용자 조회](me.md), [로그아웃](logout.md), 다른 API의 세션 인증 가드는 후속 구현 범위다. 아래 `/me` 복구 절차는 해당 API가 구현된 뒤 사용할 수 있다.

## 계정 생성 정책

- 처음 검증된 지갑이면 별도 가입 절차 없이 `users`와 `user_wallets`를 함께 생성한다.
- 새 계정의 `displayName`은 암호학적 난수 4바이트의 소문자 16진수를 붙인 `사용자-a7f29c41` 형식이다. 이름 중복을 허용하며 사용자 식별은 `users.id`로 한다. `avatarUrl`은 null이다.
- 검증된 `(chainNamespace, addressKey)`로 기존 계정을 찾는다. Solana는 주소 대소문자를 유지하고 `addressKey=address`로 저장한다. 기존 계정의 이름과 아바타는 유지한다.
- `status=active`인 계정만 로그인한다. `suspended`와 `withdrawn`은 거절하며 계정을 다시 생성하거나 지갑을 다른 계정으로 옮기지 않는다.
- 새 지갑과 기존 로그인 쿠키를 함께 제출해도 기존 계정에 자동 연결하지 않는다. 지갑 연결·계정 병합·프로필 수정은 별도 API의 범위다.

## 요청

필수 헤더는 `Origin`과 `Content-Type: application/json`이다. 요청 출처는 허용 목록과 챌린지에 저장된 URI의 요청 출처에 모두 일치해야 한다. 정의된 쿼리가 없으므로 전달된 쿼리는 모두 무시한다. 본문은 JSON 객체로 필수이며 아래 허용 필드만 남긴 뒤 검증한다. 정의되지 않은 본문 필드는 제거하고, 그 존재만으로 400을 반환하지 않는다. 프론트 요청은 `credentials: 'include'`를 사용한다.

`Content-Type`의 매체 타입은 대소문자 구분 없이 `application/json`이어야 한다. charset 생략 또는 `charset=utf-8`을 허용하며, `application/json; charset=UTF-8`도 같은 요청으로 처리한다. 헤더 누락·잘못된 매체 타입·지원하지 않는 charset은 `400 BadRequestException`이다. HTTP 계층에서 본문 파싱 전에 이 헤더를 확인하여 해당 입력이 프레임워크 기본 동작에 따라 415나 500으로 바뀌지 않게 한다.

본문 누락, 배열·문자열·숫자·불리언·null 본문은 400이다. 빈 객체나 추가 필드만 있는 객체도 필수 필드가 없으므로 400이다. 허용 필드에는 기본값, 암묵적 타입 변환, 앞뒤 공백 제거를 적용하지 않는다. 전역 DTO 정책은 `whitelist=true`, `forbidNonWhitelisted=false`, `enableImplicitConversion=false`를 유지한다. 허용 필드만 남긴 DTO를 유스케이스에 전달하며 원본 본문·쿼리는 전달하지 않는다.

| 본문 필드 | 타입 | 필수 | 검증 |
| --- | --- | --- | --- |
| `challengeId` | 문자열 | 예 | UUID v4. |
| `address` | 문자열 | 예 | Base58 32~44자, 디코딩 결과 32바이트. 대소문자 유지, 공백 거절. |
| `signedMessage` | 문자열 | 예 | 필요한 `=` 패딩을 포함한 표준 Base64. 유효한 UTF-8 원본 메시지 1~4096바이트, 인코딩 문자열 최대 5464자. |
| `signature` | 문자열 | 예 | 필요한 `=` 패딩을 포함한 표준 Base64, 정확히 64바이트를 표현한 88자. Ed25519로 검증. |

허용 필드의 값에는 Base64url, 공백·줄바꿈이 섞인 Base64, 숫자 배열, null, 암묵적 문자열 변환을 허용하지 않는다. Base64는 재인코딩하여 같은 문자열인지 확인한다. `signInInput`, nonce, domain, chainId, publicKey 등 정의되지 않은 필드는 제출되어도 제거하고 사용하지 않는다. 서명 검증의 기대 입력은 서버에 저장된 챌린지에서 읽는다.

원본 바이트 길이가 3의 배수라면 Base64에 `=`가 없어도 표준 표현이다. UTF-8로 해석할 수 없는 메시지 바이트는 대체 문자로 복구하지 않고 400으로 거절한다. 형식 검증을 통과했지만 기대 메시지·주소·서명이 일치하지 않으면 `401 AUTH_SIGNATURE_INVALID`다.

서명 결과의 실제 `account.address`를 `address`로 전달한다. `signedMessage`와 `signature`는 지갑이 반환한 Uint8Array를 그대로 Base64로 인코딩한다. 메시지를 TextEncoder로 다시 구성하지 않는다.

Wallet Standard의 메시지·필드 검증에 더해 Ed25519 서명은 엄격한 `zip215=false` 정책으로 확인한다. 개인키 없이 임의 메시지를 통과시키는 small-order 공개키와 비정규 점 표현을 거절한다. 정상 Solana 지갑이 생성한 키·서명은 같은 API를 사용한다. 검증 정책은 [noble-curves 공식 설명](https://github.com/paulmillr/noble-curves/tree/1.9.7#ed25519)을 따른다.

## 요청 쿠키 처리

| 역할 | 운영 HTTPS | 로컬 HTTP | 누락·잘못된 형식·동일 이름 중복 |
| --- | --- | --- | --- |
| 필수 챌린지 연결 쿠키 | `__Host-cameo_auth_binding` | `cameo_auth_binding` | `401 AUTH_CHALLENGE_INVALID`. 새 연결값을 생성하지 않음. |
| 선택 기존 세션 쿠키 | `__Host-cameo_session` | `cameo_session` | 기존 세션이 없는 것으로 처리하고 새 로그인 진행. |

두 쿠키의 형식은 난수 32바이트를 표현한 패딩 없는 Base64url 43자다. 길이·문자 집합·디코딩 결과 길이·재인코딩 일치를 확인한다. 같은 이름의 쿠키가 두 개 이상이면 값이 같아도 모호한 입력으로 처리한다. 첫 번째나 마지막 값 하나를 임의로 선택하지 않는다.

연결 쿠키는 SHA-256 소문자 16진수 64자 해시로 변환하여 챌린지의 `browser_binding_hash`와 비교한다. 기존 세션 쿠키도 같은 해시 표현으로 조회한다. 형식이 맞아도 해당 세션 행이 없거나 이미 폐기되었다면 새 로그인은 진행한다. 존재하는 미폐기 행은 만료 여부·사용자 ID와 무관하게 성공 트랜잭션에서 폐기한다. 기존 세션의 사용자를 새 지갑의 계정 식별이나 자동 연결에 사용하지 않는다.

로그인 실패 시 기존 세션 쿠키가 잘못되었다는 이유만으로 쿠키를 삭제하지 않는다. 성공 응답에서만 새 세션 쿠키로 교체하며, 필수 연결 쿠키의 삭제는 아래 상태 변경 표를 따른다.

## 검증 순서

1. HTTP 계층에서 `Content-Type`을 확인하고 본문 객체·허용 필드의 형식을 검증한다. 정의되지 않은 쿼리는 무시한다. 허용된 `Origin`과 필수 연결 쿠키를 확인한다. 선택 기존 세션 쿠키는 새 로그인 성공 여부를 결정하지 않는다.
2. `challengeId`로 서버의 챌린지를 읽고 존재, `auth_method=siws`, 미사용, DB 시각 기준 유효기간, 연결값 해시 일치를 확인한다.
3. `verification_payload`의 SIWS 필드 타입과 저장된 nonce·발급 시각·만료 시각·챌린지 ID의 일치를 확인한다. 저장 데이터가 손상되어 검증 기준을 구성할 수 없으면 내부 실패인 500으로 처리하며 클라이언트 값으로 보완하지 않는다. 검증된 URI의 출처와 허용된 `Origin`이 다르면 `403 AUTH_ORIGIN_NOT_ALLOWED`다.
4. SIWS 검증에서 저장된 입력과 제출 주소로 기대 메시지를 구성한다. 모든 발급 필드, 원본 메시지 바이트, 주소를 디코딩한 공개키와 Ed25519 서명을 검증한다. `notBefore`, `resources` 등 발급하지 않은 필드의 추가나 끝의 줄바꿈도 기대 바이트와 다르면 거절한다. 검증된 `(chainNamespace, address, addressKey)`만 계정 처리에 전달한다.
5. DB 트랜잭션을 시작하고 동일 `(chainNamespace, addressKey)`의 트랜잭션 자문 잠금을 획득한다. 챌린지 행을 잠근 뒤, 지갑을 다시 조회하고 기존 계정이면 사용자 행도 잠가 상태를 읽는다. 검증 전에 읽은 사용자 상태를 재사용하지 않는다.
6. 잠금을 획득한 뒤 챌린지의 인증 방식·검증용 데이터·연결값이 서명 검증에 사용한 값과 같은지 다시 확인한다. 소비 SQL에서 DB 현재 시각을 한 번 평가하여 미사용·유효기간을 조건부 검사하고 같은 시각을 `consumed_at`에 저장한다. 변경된 행이 없으면 `401 AUTH_CHALLENGE_INVALID`로 처리한다.
7. 기존 계정이 비활성이면 챌린지 소비만 커밋한다. 계정·지갑의 활동 시각, 새 세션, 기존 세션은 변경하지 않는다. 커밋이 확인된 뒤 연결 쿠키를 삭제하고 `403 AUTH_USER_UNAVAILABLE`을 반환한다.
8. 기존 활성 계정이면 ID·프로필을 유지한다. 처음 검증된 지갑이면 계정과 지갑을 함께 생성한다. 사용자 로그인 시각과 지갑 사용 시각을 갱신하고 독립적인 새 토큰 해시로 세션을 생성한다.
9. 형식이 맞는 기존 세션 토큰이 가리키는 미폐기 세션만 폐기한다. 모든 쓰기를 커밋한 뒤 새 세션 쿠키, 연결 쿠키 삭제와 HTTP 200 응답을 반환한다.

HTTP 본문 파싱·요청 제한 등 공통 처리는 이 흐름보다 먼저 실패할 수 있다. 여러 조건이 동시에 잘못된 요청의 오류 우선순위에 클라이언트가 의존하지 않는다.

### 시간과 잠금 기준

- 최초 조회의 만료 검사만으로 소비를 허용하지 않는다. 지갑 자문 잠금·챌린지 행 잠금·사용자 행 잠금 대기 후 소비 시점에 재검증한다.
- 유효 조건은 `created_at <= 판정 시각 < expires_at`이며 `consumed_at IS NULL`이어야 한다. 만료 시각과 정확히 같으면 401이다.
- 소비 SQL 안에서 `clock_timestamp()`를 한 번 평가하고 유효기간 비교와 `consumed_at`에 같은 값을 사용한다. 트랜잭션 시작 시각을 반환하는 `now()`·`CURRENT_TIMESTAMP`를 소비 만료 판단에 사용하지 않는다. 애플리케이션의 `Date.now()`도 판정 기준으로 사용하지 않는다.
- 발급·소비 시각은 밀리초 단위로 맞춰 PostgreSQL 시각을 JavaScript `Date`로 읽고 계정·세션에 저장할 때 정밀도 차이가 발생하지 않게 한다. 소비와 활동·세션 생성에는 같은 DB 판정 시각을 사용한다.
- 세션 쿠키의 `Max-Age`도 DB 현재 시각에서 남은 수명을 계산하고, 측정 후 커밋·응답까지의 경과는 앱의 단조 시계로 차감한다. 앱과 DB의 시계 차이가 쿠키 수명을 바꾸지 않게 한다.
- 기존 사용자 행은 상태 확인부터 로그인 트랜잭션 종료까지 상태 변경과 경합하지 않도록 잠근다. 잠금 대기 중 정지·탈퇴가 먼저 커밋되었다면 잠금 획득 후 읽은 비활성 상태에 따라 처리한다. 로그인 커밋 뒤의 상태 변경은 후속 인증 시 다시 확인한다.
- 트랜잭션 자문 잠금은 동일 지갑에 대해 항상 같은 키를 사용하며 커밋·롤백 시 해제한다. 잠금 획득 후 지갑을 다시 조회하고 `(chain_namespace, address_key)` 유일 제약도 유지한다.
- 같은 지갑의 서로 다른 최초 챌린지가 모두 유효하면 두 요청 모두 같은 사용자 ID로 성공할 수 있다. 예기치 않은 제약 충돌이나 DB 오류는 전체를 롤백하고 500으로 처리한다. 고아 사용자 행을 남기거나 요청 도중 새 계정에 지갑을 임의로 옮기지 않는다.

사용자 활동 갱신 대상은 `users.updated_at`, `users.last_login_at`이고 지갑 활동 갱신 대상은 로그인에 사용한 `user_wallets.last_used_at`이다. 다른 연결 지갑의 사용 시각은 바꾸지 않는다. 현재 DB에는 갱신 트리거가 없으므로 해당 쓰기에서 명시적으로 갱신한다. 세션의 `created_at`, `last_seen_at`, `expires_at`, `absolute_expires_at`은 생성 시 DB 시각과 일관된 값으로 저장한다.

### 커밋과 오류 전환

잘못된 서명은 트랜잭션 소비 전에 거절한다. 비활성 계정 결과는 트랜잭션 콜백 내부에서 예외로 던지지 않고 업무 결과로 반환하여 챌린지 소비를 커밋한다. HTTP 계층이 커밋된 결과를 받아 연결 쿠키 삭제와 403 응답으로 전환한다. 이를 콜백 내부 예외로 처리하여 소비가 롤백되는 구현은 계약 위반이다.

커밋 전 내부 오류는 전체 쓰기를 롤백한다. 커밋 확인 전에는 새 세션 쿠키나 연결 쿠키 삭제를 설정하지 않는다. COMMIT 도중 연결이 끊겨 결과를 확정할 수 없으면 500으로 처리하되 이미 DB에 반영되었을 가능성을 배제하지 않는다. 클라이언트가 500이나 네트워크 오류만으로 미소비·미로그인을 단정하면 안 된다. 확인된 커밋은 HTTP 응답 전송 실패 때문에 되돌리지 않는다.

커밋 성공을 확인한 뒤 쿠키 구성·응답 직렬화 중 내부 오류가 발생한 경우도 DB 결과를 되돌리지 않는다. 응답을 아직 전송하지 않았다면 공개 오류 500으로 처리하고, 이미 전송을 시작했다면 기존 HTTP 생명주기 처리에 따라 연결을 종료할 수 있다. 쿠키는 미전달·일부 전달·전달 여부 불명일 수 있으므로 아래 응답 유실 복구와 같은 정책을 적용한다.

## 성공 응답

HTTP 200, `Cache-Control: no-store`. 신규 가입과 재로그인 모두 같은 계약이다.

```json
{
  "statusCode": 200,
  "success": true,
  "data": {
    "user": {
      "id": "95416ea1-fcf7-4e88-a58d-3e2e88543bc8",
      "displayName": "사용자-a7f29c41",
      "avatarUrl": null,
      "wallets": [
        {
          "chainNamespace": "solana",
          "address": "6xtn9dTbszpUkeqsgaU4oQwSXBPFkGUHdQTaG2Zeoc8L"
        }
      ]
    },
    "session": {
      "expiresAt": "2026-10-08T03:00:10.000Z",
      "absoluteExpiresAt": "2026-10-31T03:00:10.000Z"
    }
  }
}
```

| 필드 | 타입과 의미 |
| --- | --- |
| `user.id` | UUID 문자열. 서비스 사용자 ID. |
| `user.displayName` | 문자열 또는 null. 새 계정은 자동 생성된 이름. 기존의 null을 허용하는 데이터는 그대로 표현. |
| `user.avatarUrl` | 문자열 또는 null. 새 계정은 null. |
| `user.wallets` | 연결된 지갑 배열. 생성 시각, 동일 시각이면 지갑 UUID 순으로 정렬. |
| `wallets[].chainNamespace` / `address` | 문자열. 현재 새로 연결하는 체인은 `solana`. 주소는 저장된 대소문자 유지. |
| `session.expiresAt` | UTC ISO 8601 문자열. 현재 미접속 만료. |
| `session.absoluteExpiresAt` | UTC ISO 8601 문자열. 새 세션 생성 시각+30일. |

null은 필드를 생략하는 의미가 아니다. 세션 ID, 토큰, 토큰 해시, 브라우저 연결값, DB 내부 상태는 응답하지 않는다. 실제 로그인에 사용한 지갑 선택 상태는 프론트가 지갑 결과에서 유지한다.

## 쿠키와 부수 효과

운영은 새 `__Host-cameo_session`, 로컬 HTTP는 새 `cameo_session`을 발급한다. 기존 브라우저 토큰을 새 세션의 토큰으로 재사용하지 않는다.

운영 프론트와 API는 같은 최상위 도메인의 서브도메인으로 분리하고 양쪽 HTTPS를 사용한다. 세션 생성 시 DB 시각을 기준으로 미접속 만료는 7일, 절대 만료는 30일 뒤다. 쿠키의 `Max-Age`는 DB 만료까지 남은 초를 올림하여 설정하며 실제 허용 여부는 DB 만료로 판단한다. 이후 활동에 따른 연장은 [현재 사용자 API](me.md)의 계약을 따른다.

```http
Set-Cookie: __Host-cameo_session=<opaque-session-token>; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax
Set-Cookie: __Host-cameo_auth_binding=; Max-Age=0; Path=/; HttpOnly; Secure; SameSite=Lax
```

운영은 Domain을 생략하고 로컬은 Secure를 생략한다. `<opaque-session-token>`은 설명용 표기다. 세션 토큰은 랜덤 32바이트의 Base64url 43자이며 SHA-256 해시만 DB에 저장한다.

성공 시 챌린지를 소비하고 연결 쿠키를 삭제한다. 비활성 계정으로 소비만 커밋한 403에서도 연결 쿠키를 삭제하되 기존 로그인 쿠키와 세션은 유지한다. 다른 브라우저의 세션은 폐기하지 않는다. 동일 지갑으로 반복 로그인해도 계정·지갑을 추가 생성하거나 이름을 바꾸지 않는다.

세션 교체는 요청에 실제 제출된 기존 토큰 하나에만 적용한다. 브라우저 연결 쿠키는 5분짜리 챌린지 연결값이며 장기적인 브라우저 ID나 브라우저별 세션 제한 키로 사용하지 않는다. 응답에는 두 `Set-Cookie` 헤더를 함께 전달하며 기존 헤더를 덮어써 한쪽을 누락하지 않는다. 토큰·연결값 원문과 해시, nonce, 원본 서명 메시지·서명은 요청 로그와 오류 상세에 기록하지 않는다.

## 동시 로그인과 세션 수

같은 챌린지의 동시 제출은 한 번만 소비할 수 있다. 패배한 요청은 `401 AUTH_CHALLENGE_INVALID`이며 쿠키를 변경하지 않는다.

서로 다른 유효 챌린지와 같은 연결값으로 동시에 로그인하면 두 요청 모두 성공할 수 있다. 각 요청은 서로 다른 새 세션을 생성하고 자기 요청에 제출된 기존 세션만 폐기한다. 공통 기존 세션이 이미 폐기되었다는 이유로 나중 요청을 실패시키지 않는다.

이 경우 새 세션 두 개가 모두 활성 상태로 남을 수 있다. 브라우저는 마지막으로 적용한 `Set-Cookie`의 토큰을 사용하며, 다른 새 세션은 해당 토큰을 제출하여 폐기하거나 미접속·절대 만료가 될 때까지 유지된다. 응답 순서로 서버의 앞선 새 세션을 찾아 폐기하거나 다른 브라우저의 세션을 일괄 폐기하지 않는다. 늦게 도착한 쿠키가 이미 폐기된 토큰을 가리키면 후속 인증은 실패하며 폐기된 세션을 복구하지 않는다.

프론트는 지갑 선택부터 챌린지 발급·서명·로그인 응답 처리까지 중복 실행을 막는다. 이 UI 제어는 서버의 단일 사용 챌린지·계정 유일 제약을 대신하지 않으며, 여러 탭 사이의 단일 활성 세션을 보장하지도 않는다.

| 상태 / 코드 | 조건 | 공개 메시지 | 소비자가 할 일 |
| --- | --- | --- | --- |
| 400 `BadRequestException` | `Content-Type` 누락·잘못된 매체 타입·charset, 본문 누락·객체가 아닌 본문·필수 필드 누락, 허용 필드의 타입·주소·Base64·UTF-8 형식 오류 또는 요청 파싱 실패 | 입력 검증 결과 또는 요청 파싱 오류 메시지 | 요청 수정. 챌린지가 유효하면 수정한 요청으로 재시도 |
| 403 `AUTH_ORIGIN_NOT_ALLOWED` | 요청 출처 누락·비허용·챌린지 요청 출처 불일치 | `허용되지 않은 요청 출처입니다.` | 프론트/API 설정 확인 |

| 401 `AUTH_SIGNATURE_INVALID` | 형식은 맞지만 서명·메시지·주소가 불일치 | `지갑 서명을 확인할 수 없습니다.` | 전송 바이트 확인 후 유효한 챌린지에 다시 서명 |

| 500 `INTERNAL_SERVER_ERROR` | DB·저장 데이터·응답 처리 등 내부 실패 | `Internal server error` | 아래 제공 단계에 맞는 복구 절차 적용. 동일 증명 자동 재전송 금지 |

  "success": false,
  "code": "AUTH_CHALLENGE_INVALID",
  "message": "로그인 요청이 유효하지 않습니다. 다시 시도해 주세요.",

오류 처리는 HTTP 상태와 `code`를 기준으로 한다. 400의 `message`는 표시·진단용이며 문구나 검증 오류의 순서를 안정 계약으로 사용하지 않는다. 내부 예외·SQL·서명 검증 도구의 상세는 공개하지 않는다.

### 재시도와 응답 유실 복구

로그인은 동일 서명 증명의 재전송을 항상 성공시키는 멱등 API가 아니다. 성공 또는 비활성 계정 결과로 챌린지가 소비되면 같은 증명으로 새 세션을 만들 수 없다.

- 400·출처 403·서명 401·429는 해당 요청으로 챌린지를 소비하지 않는다. 원인을 수정하고 챌린지·연결 쿠키가 여전히 유효하다면 같은 챌린지에 대한 올바른 증명을 다시 제출할 수 있다. 메시지·서명을 수정해야 하면 같은 유효 챌린지 입력으로 다시 서명한다.
- `AUTH_CHALLENGE_INVALID`는 기존 증명을 반복 제출하지 않고 새 챌린지와 새 서명으로 시작한다.
- `AUTH_USER_UNAVAILABLE`는 자동 재시도·자동 가입을 반복하지 않는다. 기존의 다른 계정 세션이 유지되더라도 이번 지갑 로그인 성공으로 표시하지 않는다.
- 500·네트워크 오류·응답 유실은 커밋 여부를 클라이언트가 단정할 수 없으므로 같은 증명을 자동 재전송하지 않는다. `/me` 제공 후에는 아래 복구 절차를 적용한다.

`/me`가 제공된 뒤의 복구 절차는 다음과 같다.

1. `credentials: 'include'`로 [현재 사용자 API](me.md)를 호출한다.
2. 200이면 `user.wallets`에 이번 로그인에서 선택한 `(chainNamespace=solana, address)`가 있는지 정확히 비교한다. 포함되면 해당 계정의 현재 세션을 사용한다. 포함되지 않으면 이전 계정 세션일 수 있으므로 이번 로그인 성공으로 처리하지 않는다. 선택한 지갑으로 로그인하려면 새 챌린지와 새 서명을 사용한다.
3. 401이면 새 챌린지와 새 서명으로 로그인한다. 403 `AUTH_USER_UNAVAILABLE`이면 자동 재시도를 중단한다.
4. `/me` 자체가 429·500이거나 네트워크 오류이면 로그인 성공·실패를 단정하지 않는다. 요청 제한에 맞춰 조회를 재시도하거나 사용자에게 확인 중임을 알린다.

현재 `/me`는 미구현이다. 로그인 API만 제공되는 단계에는 이 자동 복구를 호출하지 않는다. 500·응답 유실 시 성공 여부를 확정하지 않은 상태로 표시하고, 사용자가 다시 로그인을 요청하면 새 챌린지와 새 서명을 사용한다. 원래 요청이 커밋되어 추가 세션이 남을 수 있으며 이는 위 동시 세션 정책을 따른다. `/me`가 제공되면 자동 복구와 그 통합 검증을 함께 추가한다.

지갑 미설치, 사용자의 승인 취소, `signIn` 미지원은 프론트/지갑 오류다. 서버 로그인 API의 업무 오류 코드로 가장하지 않으며, 검증되지 않은 연결 상태만으로 로그인 성공 UI를 표시하지 않는다.

## 공통·DB 구현

아래 공통 오류 처리와 DB 기준 SQL을 로그인 구현에 포함했다.

- `BusinessErrorKind`에 인증 실패를 나타내는 `unauthorized`를 추가하고 공통 HTTP mapper에서 401·`Unauthorized`로 변환한다. 공개 `code`와 `message`는 위 계약을 사용한다. 유스케이스가 Nest HTTP 예외나 응답 객체에 의존하지 않게 한다.
- `db/migrations/2026-10-01-01-auth-challenges.sql`과 `2026-10-01-02-auth-wallet-accounts-and-sessions.sql`이 챌린지·계정·지갑·세션 테이블을 재현한다. 빈 개발 DB와 테스트 임시 스키마에서 같은 계약을 실행할 수 있다.
- 기준 SQL은 현행 컬럼·FK·계정 상태 제약·지갑 유일 제약·토큰 해시 유일 제약·시각 제약·인덱스·RLS 설정을 재현한다. 기존 테이블이나 데이터를 삭제·초기화하지 않으며 앱 시작 때 자동으로 적용하지 않는다. 기존 스키마와 차이가 있으면 별도 변경으로 명시한다.
- 로컬 접속 역할은 테이블 소유자라 RLS를 우회하며 현재 네 테이블에는 RLS 정책이 없다. 로그인 실행 환경의 DB 역할이 필요한 읽기·쓰기 권한을 갖는지 확인한다.

| 소유 책임 | 사용하는 상태·규칙 |
| --- | --- |
| `challenge/` | 발급 입력·연결값 검증 기준, 챌린지 조회·행 잠금·조건부 소비. 발급·로그인에서 같은 연결값 형식과 해시 정책을 사용. |
| `siws/` | 입력 생성과 증명 검증, 검증된 Solana 주소 반환. 기대 입력은 DB 값이며 지갑 브랜드로 분기하지 않음. |
| `wallet-account/` | 지갑 기준 잠금·재조회·계정 상태 확인, 최초 계정과 지갑 생성, 활동 시각 갱신. |
| `session/` | 새 토큰·해시·7일/30일 만료 정책과 저장, 제출된 기존 세션의 폐기. |
| `login/` | 위 책임을 조합하는 업무 흐름과 하나의 트랜잭션, 커밋된 성공·비활성 계정 결과, HTTP DTO·쿠키·응답 처리. |

저장소는 같은 불투명 `TransactionContext`에 참여하고 내부에서 별도 트랜잭션을 열지 않는다. 비활성 계정 결과를 포함해 커밋 여부는 유스케이스가 결정하고, 컨트롤러는 확정된 결과에 맞춰 쿠키와 HTTP 응답을 처리한다.

## 완료 검증

구현 당시 Node `crypto`로 만든 독립 Ed25519 증명과 실제 PostgreSQL의 임시 스키마로 검증했다. 신규·기존 계정, 입력·출처·쿠키 오류, 특수 공개키 위조 거절, 경합·잠금 중 만료·상태 변경, 커밋 실패 롤백, 커밋 후 쿠키 처리 실패, 앱 시계 오차와 로그의 비밀값 제외를 확인했다. 전체 테스트 59개 통과 후 테스트 코드와 실행 스크립트를 저장소에서 제거했다. 이 기록은 구현 당시 검증 이력이다.

실제 Phantom·추가 지갑 앱의 브라우저 연동은 프론트 통합 시 확인한다. COMMIT 확인 불명과 네트워크 응답 유실을 직접 재현한 검증, `/me`를 이용한 클라이언트 복구는 후속 통합 검증 범위다. 아래 항목에는 그 후속 확인도 포함한다.

- 실제 Phantom 서명으로 계정·지갑·세션과 쿠키가 생성되고 재로그인 시 기존 ID·이름을 유지하는지 확인한다.
- 같은 형식의 유효한 SIWS 증명은 지갑 브랜드 필드 없이 검증되는지 확인한다. `wallet`, `provider`, `isPhantom` 등의 추가 필드는 제거되며 성공·실패 판단에 영향을 주지 않아야 한다.
- 다른 지갑 앱에서 같은 Solana 주소의 증명을 제출해도 기존 ID·이름을 유지하는지 확인한다. 실제 추가 지갑의 지원 상태는 해당 지갑으로 호환성을 확인한 뒤 기록한다.
- 추가 쿼리를 무시하고, 본문의 추가 필드를 제거한 뒤 유효한 허용 필드로 로그인하는지 확인한다. 제거한 `signInInput`, nonce, domain 등의 값이 서명 검증이나 계정 생성에 영향을 주지 않는지 확인한다.
- `application/json`과 `application/json; charset=utf-8`을 허용하는지 확인한다. `Content-Type` 누락·잘못된 매체 타입·지원하지 않는 charset은 쿠키 변경 없이 공개 400이어야 한다.
- 본문·필수 필드 누락, 객체가 아닌 본문, 허용 필드의 잘못된 값은 400인지 확인한다. 정의되지 않은 필드만 보낸 본문도 필수 필드가 없으므로 400이다. Base64 재인코딩 일치와 메시지 길이·UTF-8·서명 길이 경계를 확인한다.
- 연결 쿠키 누락·잘못된 형식·같은 이름 중복·해시 불일치는 401인지 확인한다. 선택 기존 세션 쿠키의 누락·잘못된 형식·중복·미존재·기폐기는 새 로그인 성공을 막지 않는지 확인한다.
- 저장된 SIWS 입력과 다른 domain, uri, nonce, chainId, 시간, requestId, 주소, 메시지와 서명을 거절한다.
- 같은 서명 증명의 동시 제출은 한 번만 성공하며 같은 지갑의 서로 다른 최초 챌린지는 계정 하나에 연결되는지 확인한다.
- 자문 잠금·챌린지 행 잠금·사용자 행 잠금 대기 중 만료된 요청은 401인지 확인한다. 만료 시각과 정확히 같은 경우도 거절하고 소비 시각 제약 오류로 500이 되지 않는지 확인한다.
- 기존 계정의 정지·탈퇴가 먼저 커밋된 경우 상태를 다시 읽어 챌린지 소비만 커밋하는지 확인한다. 비활성 결과에서 활동 시각·기존 세션·새 계정은 변경하지 않아야 한다.
- 실패별 상태 변경 표의 DB 상태와 두 쿠키를 확인한다. DB 쓰기·커밋 실패로 롤백이 확인되면 모든 쓰기와 기존 세션 폐기가 롤백되고 쿠키를 발급·삭제하지 않아야 한다.
- 커밋 확인 후 응답 처리 오류는 확정된 소비·계정·세션 상태를 되돌리지 않는지 확인한다. COMMIT 확인 실패와 응답 유실을 성공으로 가장하거나 같은 증명으로 자동 재시도하지 않아야 한다.
- 서로 다른 챌린지의 동시 성공은 같은 지갑이면 같은 사용자 ID, 독립적인 세션을 만드는지 확인한다. 공통 기존 세션의 폐기는 한 번만 적용하며 다른 브라우저 세션은 유지한다.
- 새 로그인은 제출된 기존 세션만 폐기하고 토큰·해시·서명·연결값·nonce가 JSON과 로그에 노출되지 않는지 확인한다. `signInInput`의 공개 nonce는 챌린지 API 응답에서만 사용하는 값이다.
- 기존 데이터·테이블을 유지하면서 기준 SQL을 재적용할 수 있고, 실제 PostgreSQL의 격리된 임시 스키마에서도 신규 가입·재로그인·경합·롤백 계약을 검증하는지 확인한다.
- `/me` 구현 이후에는 응답 유실·500 복구를 함께 검증한다. 이전 계정의 `/me` 200을 선택한 새 지갑의 로그인 성공으로 오인하지 않아야 한다. 구현 전에는 `/me` 자동 복구를 제공한다고 표시하지 않는다.
