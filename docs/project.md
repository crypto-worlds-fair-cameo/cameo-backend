# cameo 프로젝트 개요

해당 프로젝트는 [https://colosseum.com/worldsfair](https://colosseum.com/worldsfair) 에서 진행하는 Crypto World's Fair (Solana Track) 참가를 목적으로 한다.

## 1. 프로젝트 한 줄 설명

제한된 획 수 규칙으로 모두가 함께 완성하는 실시간 협업 캔버스

## 2. MVP 구현 스택 및 아키텍처

- 프론트엔드: React + Vite
- 백엔드: Node.js + NestJS + Express
- 데이터베이스: PostgreSQL (pg)
- 지갑/온체인 연동: Solana wallet auth/signature verification 기반
- 목표: 짧은 기간 내 데모 가능한 MVP 구현, 인증·기여 기록·시즌 상태를 빠르게 검증할 수 있는 구조로 설계

## 3. 참가/팀 맥락

- 해커톤: Colosseum Arena Hackathon (Solana Track)
- 팀 구성: 기획 1 / 디자인 1 / 개발 1
- 목표: 짧은 기간 내 데모 가능한 MVP 완성

## 4. 핵심 기능

### A. 메인 도화지 (Global Canvas)

- 단일 고정 캔버스: **10000px x 10000px**
- 회원 정책: -
- 그리기 정책: 계정당 평생 **1획** (마우스 다운 ~ 업 1회)
- 오버드로우 허용: 기존 획 위에 덮어 그리기 가능
- 히스토리: **1시간 단위** 스냅샷 캡처 및 조회

소켓 연결과 인증은 [프론트 연결 가이드](api/canvas/realtime-connection.md), 좌표 전송·방송·복구는 [그림 동기화 가이드](api/canvas/drawing-sync.md)를 따른다. 메인 캔버스는 계정당 평생 1획을 집행하며, 좌표 묶음을 PostgreSQL에 저장한다. 1시간 단위 히스토리 스냅샷은 후속 단계다.

획 사용은 첫 좌표를 승인할 때 차감하며, 중간에 연결이 끊겨도 사용한 것으로 계산한다. [획 사용 기록 마이그레이션](../db/migrations/2026-10-03-01-canvas-stroke-usages.sql)과 [좌표 묶음 마이그레이션](../db/migrations/2026-10-04-01-canvas-stroke-chunks.sql)을 소켓에 연결했다. 정상 완료 시 마지막 좌표와 완료 시각을 함께 저장한다.

서버는 새 좌표를 즉시 방송하고, 주기 또는 누적량 기준으로 좌표 묶음을 저장한다. 저장된 좌표는 DB에서 복구하고, 아직 저장하지 않은 최신 좌표는 현재 서버 메모리에서 함께 복구한다. 저장 성공한 좌표는 메모리 대기열에서 제거한다. 저장 대기열과 최근 좌표 캐시는 크기를 제한하므로 누적 그림 전체가 서버 메모리를 계속 점유하지 않는다. 저장 실패한 좌표는 대기열에 남아 재시도한다. 대기열이 가득 차면 새 append를 잠시 거절한다.

정상 종료는 대기 중 좌표 저장을 시도한다. 프로세스 강제 종료·저장 장치 장애에서는 아직 저장하지 않은 최신 좌표가 유실될 수 있지만, 첫 승인으로 사용한 획은 복원되지 않는다. sync는 시작할 때 고정한 순서 범위만 페이지로 반환해, 저장 중에도 페이지 사이에 누락이나 중복이 생기지 않게 한다. 여러 소켓 서버 인스턴스 간 실시간 공유와 스냅샷 압축은 아직 지원하지 않는다.

저장은 기본 1초·256묶음·1MiB 기준으로 실행한다. 저장 대기열과 최근 좌표 캐시는 각각 16MiB·4096묶음, 마지막 획 상태 캐시는 8MiB·2048획 이내로 유지한다. 바이트 한도는 직렬화된 데이터 크기 기준이다. DB 커밋 응답이 유실되면 실제 기록을 확인하고, 확인할 수 없는 동안 새 순서를 발급하지 않는다. 정상 완료 획 순서와 저장된 좌표 묶음 순서는 별도로 관리한다.

### B. 시즌 도화지 (Season Canvas)

- 기간 기반 이벤트 캔버스 (시작/종료 시각 존재)
- 참가 방식: 기간 내 **참가 신청자 전원 참여 가능** (주최자 개별 승인 없음)
- 획 제한: 주최자가 사용자당 N획 직접 설정 (**1~1000**)
- 종료 처리: 종료 시점에 그리기 종료 및 결과물 확정

## 5. 시즌 보상 자산 방식 (권장안 + 비교)

### 권장안 (MVP)

1. 완성 캔버스를 대표하는 **cNFT 1개** 민팅
2. 참가자 전원에게 **참여 증명 cNFT** 1개씩 지급

### 비교: 옵션 1 vs 옵션 2

- 옵션 1(권장): 대표 cNFT + 참여증명 cNFT 배포
  - 장점: 구현/설명 단순, 참여 증명 명확, 해커톤 데모 적합
  - 단점: 경제적 분할 소유 구조는 약함
- 옵션 2: 완성작 분할 소유 토큰 구조
  - 장점: 소유권/경제성 서사 강화
  - 단점: 토크노믹스/법적 해석/설계 복잡도 증가, MVP 리스크 큼

## 6. MVP 성공 기준

- 메인 도화지: 회원이 실제로 1회만 그릴 수 있고 히스토리가 누적된다.
- 시즌 도화지: 신청/참여/종료 흐름이 동작하고, 종료 후 자산 분배가 성공한다.
- 데모 관점: 사용자 여정(가입→지갑연결→그리기→시즌종료→지갑 수령)이 끊기지 않는다.
